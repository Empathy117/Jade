# 档案模块设计：人物图谱与互动地图（codex.json）

状态：已实施（M1 契约与校验、M2 档案面板、M3《生尸之死》档案，2026-08-21；
M4《红楼梦》档案，2026-08-22——99 人物 / 57 关系 / 宁荣两谱系 / 33 地点 /
两张示意地图，规模压力下分组列表可用，搜索仍留作未来扩展）。
起因：《生尸之死》的三张原书附图（家族谱系图 p0113、微笑墓园地图 p0161、
殡仪馆西侧示意图 p2173）是约 500px 的低清扫描。重绘只解决清晰度，
不解决真正的需求——读者在阅读中反复要回答的两个问题：
**「这个人是谁来着」**和**「这个地方在哪来着」**。

## 0. 一句话

新增一个可选的每书契约 `codex.json`（档案），描述人物、关系、地点与地图；
Reader 增加一个「档案」面板（人物 / 地图 / 图册三页签），全部内容随阅读
进度按段落锚点逐条解锁——**正文没说的，档案不说**。

## 1. 背景与动机

- 文字层面的交互过多会打断读原文的心流，所以正文保持零侵入；但「查人物、
  查地图」这类交互恰恰是**回到心流的最短路径**——纸书读者本来就会翻回
  卷首的谱系图。把这件事做好，是增强而不是干扰。
- 复用价值明确：《红楼梦》466 个场景、41 个地点标签、数百人物，正是
  人物图谱的经典受益者；此后每本书都可以选配。
- 基础设施已经在位：
  - `furthestReadIndex` + 段落位置索引是现成的解锁原语（资料图册与章节
    目录都在用）；
  - `direction.json` 每个场景已有 `location` 标签（本书 113 场景 / 37 个
    地点）——地图的「你在这里」可以直接复用，零新增标注成本。

## 2. 设计原则（不可违反）

1. **正文没说的，档案不说。** 档案里每一个可显示的原子（人物条目、别名、
   一条事实、一条关系、一次状态变化、一个地图标记、一张地图本身）都携带
   一个段落锚点 `at`；只有 `pos(at) <= furthestReadIndex` 时才可见。
   不显示总数（「已解锁 3/47 人」会剧透卡司规模），不显示锁定占位符
   （「???」暗示还有秘密，本身就是信息）。未解锁 = 不存在。
2. **阅读流零侵入。** 所有新交互收在档案面板内。正文中唯一的触点仍是
   既有的行内附图缩略图，不新增人名链接、不新增悬浮卡。
3. **书是数据，Reader 是通用运行时。** 新能力 = 新契约 + 通用组件；
   不为任何一本书写专属代码。`codex.json` 与 `guide.json` 一样可选，
   没有它的书行为完全不变。
4. **忠实原书。** 重绘地图必须忠实原图的布局与标注；原扫描图保留在图册
   作为出处，一键可对照。信息节奏也尊重原书：殡仪馆平面图在原书 p2173
   才给出——那是推理小说作者刻意的信息设计，档案里的这张地图就也在
   那里才解锁（此前去过的房间只出现在地点列表里，没有几何信息）。

## 3. 数据契约：`codex.json`

与 `guide.json` 平级的可选文档。人物、关系、谱系、地点、地图放在同一个
文档里，因为它们互相引用（关系↔人物、标记↔地点、谱系↔人物），共享同一套
解锁语义，也共享一次校验。`guide.json` 保持现状（首选起点 + 图册）不动。

```jsonc
{
  "schema_version": 1,
  "book_id": "death-of-the-living-dead",
  "source_revision": 1,
  "source_sha256": "…",

  "characters": [
    {
      "id": "char_grin",
      "name": "弗朗西斯·巴里科恩",
      "at": "p0121",                      // 解锁锚点 = 首次登场，也是跳转目标
      "aliases": [
        { "name": "格林", "at": "p0130" } // 别名有自己的揭示时刻
      ],
      "group": "巴里科恩家",               // 列表分组；也用于多谱系书
      "portrait": "codex-assets/grin.jpg", // 可选
      "role": "史迈利的孙子",              // 一句话身份，随 at 一起解锁
      "facts": [
        { "text": "在纽约组朋克乐队，与祖父闹翻后离家。", "at": "p0135" }
      ],
      "status": [                          // 状态时间线：本书的招牌
        { "label": "死亡", "kind": "dead",   "at": "p0409" },
        { "label": "再生", "kind": "undead", "at": "p0466" }
      ]
    }
  ],

  "relationships": [
    {
      "a": "char_smiley", "b": "char_monica",
      "kind": "spouse",                    // spouse | parent | 其他自由 kind
      "label": "再婚",                     // 可选展示文本
      "at": "p0113"                        // 关系也可以是被揭示的秘密
    }
  ],

  "trees": [                               // 谱系图：作者手排布局，不自动布局
    {
      "id": "tree_barleycorn",
      "title": "巴里科恩家族",
      "at": "p0113",                       // 原书谱系图出现处 = 结构整体揭示处
      "nodes": [
        { "character_id": "char_thomas", "row": 0, "col": 3 }
      ]
      // 夫妻横条与亲子连线由 relationships 里 kind=spouse/parent 推出
    }
  ],

  "places": [
    {
      "id": "managers_office",             // 与 direction.json 的 location 同一命名空间
      "name": "经理办公室",
      "parent": "funeral_home",            // 层级：房间 ⊂ 建筑 ⊂ 区域
      "at": "p2101",
      "facts": [{ "text": "…", "at": "p2140" }]
    }
  ],

  "maps": [
    {
      "id": "map_funeral_west",
      "title": "殡仪馆西侧",
      "at": "p2173",                       // = 原书示意图锚点：书讲到哪，图开到哪
      "source_illustration_id": "ill0003", // 出处：原扫描图，一键对照
      "image": "codex-assets/map-funeral-west.svg",
      "width": 1000, "height": 750,
      "markers": [
        { "place_id": "managers_office", "x": 130, "y": 210 }
      ]
    }
  ]
}
```

### 解锁语义（运行时唯一规则）

```
visible(atom) := sourcePositions[atom.at] <= furthestReadIndex
```

- 人物可见后，其 role 同时可见；facts / aliases / status 各自再按自己的
  `at` 逐条解锁。人物未解锁时，指向它的关系、谱系节点一并不可见。
- 谱系树在 `tree.at` 通过后整体显示**结构与姓名**（原书的谱系图本来就
  一次性揭示了全家结构——这正是本格推理的公平性惯例），但每个人的
  事实与状态仍按各自锚点解锁；树上尚未登场的人物，人物卡只显示
  「尚未登场」与树上可见的关系。
- 前置内容里的锚点（如 p0113 的谱系图）位置先于首选起点 p0114，因此
  即使读者跳过前置内容也天然自始解锁——与原书把谱系图放在卷首的
  意图一致，无需特殊处理。
- 解锁只看 `furthestReadIndex`：知识不回锁。回读早期章节时，树上显示的
  死亡标记是「你已经知道的」，这与资料图册现状一致。

### 与 direction.json 的地点对齐

`places[].id` 尽量沿用 `direction.json` 的 location 标签
（`managers_office`、`route_113`…）。相同 id 自动获得两个免费能力：

- **你在这里**：当前段落所在场景的 location 若出现在某张地图上，该标记
  高亮呼吸（跟随 `currentIndex`，回读时指向你正读到的地方）。
- **地点卡的「已读场景」**：列出 direction 中该地点、且
  `start <= furthestReadIndex` 的场景（标签 + 跳转），未读场景不出现。

地点可以比场景标签更细（一个房间没有独立场景也可以入册），此时没有
上述联动，仅作图鉴条目，属正常情况。

### 校验器扩展（pipeline）

- 所有 `at` 段落号存在于 source；
- `relationships` / `trees` / `markers` 的 id 引用全部可解析；
- `maps[].image` 文件存在（放在 `codex-assets/`，非 Director 素材目录）；
- `source_illustration_id` 存在于 source.illustrations；
- 树节点 `(row, col)` 无重复占位；spouse 关系在树中相邻可渲染；
- 与 guide 相同的 `source_revision` / `source_sha256` 钉扎。

## 4. Reader 运行时

### 信息架构

顶栏的「图」按钮升级为「档」——档案面板，三个页签：

- **人物**：谱系图 + 分组人物列表（大卡司时带搜索）→ 人物卡
- **地图**：地图列表 + 缩放平移查看器 + 标记 → 地点卡
- **图册**：现有 ReferenceGallery 原样并入（原书扫描图 = 出处层）

按钮在任何页签有内容解锁后出现；有新解锁时按钮出现一个小圆点，面板内
对应条目带「新」标（localStorage 记录每书每修订的已读集合）。不弹 toast，
不打断阅读——这是默认，也是唯一行为。

### 人物页

- 谱系图为 SVG，从 `trees[].nodes` 的行列格 + spouse/parent 关系渲染：
  夫妻用双线横条，子女从婚线中点垂下总线。**不做自动布局**——复杂婚配
  （史迈利两任妻子）会让自动布局既难又不稳定，而原书谱系图就是现成的
  ground truth，转写成行列格是一次性的低成本工作，渲染结果永远确定。
- 节点上叠当前状态徽记（†、再生等，取最新已解锁 status）。
- 人物卡：姓名与已解锁别名、身份、状态时间线（每条可跳回原文）、事实
  列表（每条可跳回原文）、关系条目（点击跳到对方卡）、「首次登场 →」。
- 不入树的人物（村民、警方、访客）按 `group` 分组列表显示。

### 地图页

- 单指拖动平移、双指/滚轮缩放（CSS transform，含 reduced-motion 降级）。
- 标记按地点解锁逐个出现；点击 → 地点卡（名称、事实、已读场景跳转）。
- 「你在这里」呼吸高亮 + 打开面板时自动定位到含当前位置的地图。
- 右上「查看原书扫描 →」切到图册页签并选中对应原图。

### 交互接线（App.tsx）

- `codexOpen` 并入现有面板互斥组（settings/history/chapters）与 Esc 处理；
  面板内点击不触发翻页（沿用 `data-interactive` 约定）。
- 跳转沿用 `jumpToReference` 语义：目标在阅读地板之下时先降地板。
- 纯逻辑收在 `codex.ts`（解锁过滤、树布局解析、seen 记录），全部可单测；
  组件为 `CodexPanel` / `FamilyTree` / `BookMap` / `CharacterCard` /
  `PlaceCard`。

## 5. 三张原图的去向

| 原图 | 新形态 | 原扫描图 |
| --- | --- | --- |
| 家族谱系图（p0113） | 数据（tree + relationships），交互渲染 | 图册保留，出处 |
| 微笑墓园地图（p0161） | 重绘 SVG + 标记 + 你在这里 | 图册保留，出处 |
| 殡仪馆西侧示意图（p2173） | 重绘 SVG + 标记 + 你在这里 | 图册保留，出处 |

SVG 重绘规范：忠实原图布局与全部标注；线稿用 CSS 变量取色以随主题；
`viewBox` 与 markers 坐标同一坐标系；重绘完成后逐项对照原扫描图核对
（房间数、门的位置、标注文字），核对记录写入 production-notes。

## 6. 生产流程变化

- 协议新增 **Step 1.6 — 可选档案（codex.json）**，紧随 Step 1.5 Guide：
  1. 以前置内容（登场人物表、卷首谱系图）为骨架建人物与关系；
  2. 每条信息锚在**正文首次揭示处**；通读时顺手记录（与导演分析同一遍）；
  3. 只写正文明说的事实，不写推断，不写元信息（“此人很可疑”是剧透）；
  4. 状态变化（死亡/复活/失踪）必须有锚点；
  5. 地点 id 沿用 direction 的 location 标签；
  6. 地图重绘忠实原图；`source_illustration_id` 必填（有原图时）。
- AGENTS.md 增补一条不可违反规则：档案内容不得先于其正文锚点暴露。
- `just validate` 覆盖 codex 交叉校验。

## 7. 分期

- **M1 契约与逻辑**：`contracts/codex.schema.json`、校验器、`codex.ts`
  解锁过滤 + 树布局解析 + 测试。无 UI，`just check` 全绿。
- **M2 档案面板**：三页签 UI、App 接线、样式、组件测试；图册并入。
  用 restaurant-demo 或 fixture 数据自测。
- **M3 《生尸之死》档案**：编写 codex.json（约 30 人物 / 关系 / 状态
  时间线，两张 SVG 地图重绘 + 标记），`just validate`，真机体验会话
  （experience-gate：解锁顺序、你在这里、跳转、缩放、回图册出处）。
- **M4 《红楼梦》档案**（复用验证）：四大家族多谱系、41 地点对齐、
  大卡司搜索。规模压力测试后再定是否需要虚拟化。

## 9. 已定与待定

已按本文档拍板（有异议请在评审中提出）：

- 单契约 `codex.json`，不拆多文件，不并入 guide；
- 「图」按钮升级为「档」，图册并入第三页签（顶栏不再加新按钮）；
- 谱系图作者手排行列格，不做自动布局；
- 解锁 = furthestReadIndex，不显示总数与锁定占位；
- 地图整体解锁跟随原书示意图锚点，尊重原书信息节奏。

用户已确认（2026-08-21）：

1. 《生尸之死》档案做**登场人物表级别**：身份（role）+ 状态时间线；
   `facts` 字段保留在契约中，但本书的事实条目由用户日后自行编写。
2. **终极剧透不入档**：凶手身份揭露、诡计说明等结局级信息不写入
   codex.json——即使锚在揭露章之后也不写。状态时间线只记录
   死亡 / 再生 / 失踪这类剧情事件本身，不记录「谁是凶手」。
3. UI 名确定为「档案」。
